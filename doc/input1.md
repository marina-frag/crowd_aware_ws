### B1. Κενά 3–5 δεικτών: χάνονται ελεύθερα paths (`src/clustering.cpp:279-299`)
```cpp
cluster_indexes.push_back(free_path_indexes[0]);
for (int k = 1; k < free_path_indexes.size(); k++) {
  Dind = free_path_indexes[k] - cluster_indexes.back();   // απόσταση από το ΤΕΛΕΥΤΑΙΟ ΜΕΛΟΣ
  if (Dind > cluster_separation) {                      // > 5: κλείσε cluster, ξεκίνα νέο
    ... cluster_indexes.clear(); cluster_indexes.push_back(free_path_indexes[k]);
  }
  else if (Dind <= 2)                                   // <= 2: πρόσθεσε στο cluster
    cluster_indexes.push_back(free_path_indexes[k]);
  // Dind = 3,4,5: τίποτα. Το path ούτε μπαίνει ούτε ξεκινά νέο cluster.
}
```
**Μηχανισμός**:
1. Το `Dind` μετριέται από το `cluster_indexes.back()`, δηλαδή από το τελευταίο path που **μπήκε** στο cluster.
2. Ένα path με Dind = 3..5 δεν μπαίνει, άρα το `back()` δεν προχωρά.
3. Το επόμενο ελεύθερο path μετριέται από το ίδιο παλιό σημείο, και το Dind του είναι κατά 1 μεγαλύτερο.
4. Αυτό επαναλαμβάνεται μέχρι το Dind να ξεπεράσει το 5. Εκεί ξεκινά νέο cluster.

Τα ελεύθερα paths στο ενδιάμεσο δεν ανήκουν σε κανένα cluster.

**Αναπαραγωγή** (ελεύθερα 10–24, `cluster_separation = 5`):

| μπλοκαρισμένα | upstream | κατά το paper |
| --- | --- | --- |
| 13 | [10–24] (Dind = 2) | [10–24] |
| 13,14 | [10–12], [18–24]· **χάνονται 15,16,17** | [10–24] |
| 13–16 | [10–12], [18–24]· χάνεται το 17 | [10–24] |
| 13–17 | [10–12], [18–24] | [10–12], [18–24] |

**Συνέπειες**:
- Στην πράξη το cluster σπάει με **2** μπλοκαρισμένα paths, όχι με 6.
- Έως 3 ελεύθερα paths εξαφανίζονται, και ο controller δεν μπορεί να τα επιλέξει.
- Στο τέλος του βρόχου το πλάτος υπολογίζεται με `free_path_indexes.back()`, που μπορεί να είναι path που πετάχτηκε.
- Στα διαγνωστικά του fixed, ο κωδικός −4 («min span») περιλαμβάνει και αυτά τα paths. Η σημείωση μπαίνει πια και στο `metrics_summary.py`.

**Χαρακτηρισμός**: το paper (§3.3) ορίζει *«Two paths Pi, Pj (i > j) belong to the same cluster if i − j ≤ Csep»*. Το B1 είναι επομένως **απόκλιση του κώδικα από τον ορισμό του paper**, όχι σχεδιαστική επιλογή. Αυτό στηρίζει τον χαρακτηρισμό «bug». Ο fixed το κρατά (baseline = κώδικας upstream). Ο dynamic ομαδοποιεί σωστά.

### Β2. Διπλά IDs όταν σε ένα frame εμφανίζονται ≥ 2 νέα clusters (`src/clustering.cpp:185-204`)
```cpp
if (cluster_num > prev_cluster_num) {
  unsigned int j = 0;
  std::vector<unsigned int>::iterator it;
  it = std::find(prev_ids.begin(), prev_ids.end(), j);   // (1) υπολογίζεται ΜΙΑ φορά
  for (auto &cl : group.clusters) {
    j = 0;                                               // (2) το j μηδενίζεται σε κάθε cluster...
    if (cl.id == 100) {                                  //     (100 = «δεν αντιστοιχίστηκε»)
      while (it != prev_ids.end()) {                     // (3) ...αλλά το it όχι
        j++;
        it = std::find(prev_ids.begin(), prev_ids.end(), j);
      }
      cl.id = j;
      prev_ids.push_back(j);
    }
  }
}
```
**Μηχανισμός**:
1. Για το **πρώτο** νέο cluster, το `while` προχωρά το j μέχρι να βρει ID που δεν υπάρχει. Τότε `it == end()`.
2. Για το **δεύτερο** νέο cluster, το j γίνεται 0 στο (2), αλλά το `it` είναι ακόμα `end()`. Το `while` δεν εκτελείται, και το cluster παίρνει **ID 0**, ακόμα κι αν το 0 υπάρχει ήδη.

| prev_ids | μετά το matching | upstream | σωστό |
|---|---|---|---|
| [0] | [0, νέο, νέο] | [0, 1, **0**] | [0, 1, 2] |
| [1] | [νέο, 1, νέο, νέο] | [0, 1, **0, 0**] | [0, 1, 2, 3] |
| [0,1] | [0, νέο, 1, νέο] | [0, 2, 1, **0**] | [0, 2, 1, 3] |

**Συνέπεια**: ο estimator κάνει match στο **πρώτο** cluster με το ίδιο ID. Το δεύτερο δεν παίρνει ποτέ το sticky prior (92 %).

**Χαρακτηρισμός**: σαφές bug. Το paper λέει τα νέα IDs να δίνονται *«ranging from one up, disregarding the already numbered ones»*. Ο fixed το κρατά. Ο dynamic είναι διορθωμένος και στους δύο τρόπους αντιστοίχισης.

## dwal_generator node

- Δειγματοληπτεί καμπυλότητες σε σταθερό **γωνιακό** βήμα στα 1.8 m (`alpha = 0.05 m` χορδή).
- Το εύρος τους βγαίνει από το **dynamic window**: `v ∈ [v−a·Δt, v+a·Δt]`, `ω ∈ [ω−α_ω·Δt, ω+α_ω·Δt]`, με `Δt = sim_period = 0.2 s`. Καμπυλότητα = ω/v στα άκρα, με όριο ±4.
- Κάθε path είναι **arc-line**: τόξο έως 90°, μετά εφαπτόμενη ευθεία (paper §3.2). Ελέγχεται με το footprint του iWalk.
- Επειδή το εύρος αλλάζει με την ταχύτητα, το πλέγμα **μετακινείται** από frame σε frame: ο δείκτης k δεν είναι η ίδια καμπυλότητα σε δύο frames.
- **`DS = 0.05 m` και στους δύο τρόπους** (το dynamic είχε 0.02). Τώρα fixed και dynamic διαφέρουν μόνο στη λογική clustering/αποδοχής (`config/controllers/dwal.yaml: dwal_generator/DS`).
- Κόστος path = μέγιστο κόστος footprint κατά μήκος του (paper: εξασφαλίζει απόσταση από εμπόδια). Fixed: ως το R του level. Dynamic: σε όλο το ελεύθερο μήκος.
- Το log `"Braking timing"` πέρασε από INFO σε DEBUG.

## dwal_clustering node

### Cluster definition

Ένα cluster είναι **ένα σύνολο κινηματικά εφικτών, ελεύθερων paths που αντιστοιχούν στην ίδια επιλογή κίνησης** (paper: «path equivalence classes»). Όταν υπάρχει εμπόδιο μπροστά, οι επιλογές είναι τρεις:
- προς το εμπόδιο (με φρενάρισμα πριν από αυτό),
- δεξιά του,
- αριστερά του.

✅ Πού μπαίνουν τα papers («το από κάτω»): κάθε μηχανισμός αιτιολογείται από άλλη πηγή.

|     | Μηχανισμός | Κώδικας | Fixed | Dynamic | Αιτιολόγηση |
| --- | --- | --- | --- | --- | --- |
| Α   | Φίλτρο αποδοχής | fixed: `colission_r > R`, dynamic: `min(L, m + π/(2\|κ\|)) ≥ S_req(v)` | σταθερό R | μεταβλητό | **DWA, admissible velocities** (Fox 1997). Όχι ND |
| Β   | Κενό δεικτών > `cluster_separation` | `index − previous > Csep` | με B1 | σωστά | **Paper §3.3**. Αναλογία με VFH/Follow-the-Gap (valley = συνεχόμενα ελεύθερα δείγματα) |
| Γ   | Άλμα μήκους > `length_jump_threshold` | `\|L_i − L_{i−1}\| > 0.30` | όχι | ναι | **Nearness Diagram** (ασυνέχεια βάθους) και **TangentBug** (ασυνέχειες της range function) |
| Δ   | Ελάχιστο πλάτος | χορδή ≥ `min_cluster_span` | ναι | ναι | **Paper §3.3** (0.2 m). Admissible Gap Navigation: γιατί όχι ίσο με το πλάτος του ρομπότ |

Ο fixed ομαδοποιεί όπως το VFH/FGM: δυαδικό κατώφλι σε σταθερό ορίζοντα. Ο dynamic έχει ορίζοντα που εξαρτάται από την ταχύτητα, άρα χρειάζεται και ασυνέχειες βάθους (ND/TangentBug) για να ξεχωρίσει το «προς το εμπόδιο» από το «δίπλα του». **Το ND αιτιολογεί μόνο το Γ.** Το μεταβλητό r (Α) το αιτιολογεί το DWA.

### Clustering logic
#### α. Κενό στους δείκτες: `cluster_separation = 5`

$$
i_k - i_{k-1} > \texttt{cluster\_separation}
$$

- Ακέραιος, σε δείκτες δειγμάτων.
- Ένα κενό σημαίνει ότι ενδιάμεσα paths απορρίφθηκαν (φρενάρισμα, άκυρη γεωμετρία, slicing). Με την τιμή 5, έως 5 συνεχόμενα απορριφθέντα δεν σπάνε την ομάδα (στον dynamic· ο fixed σπάει ήδη με 2, B1).
- 5 δείγματα ≈ 0.25 m χορδής στα 1.8 m.
- ==🔴Αιτιολόγηση: paper §3.3 (ο ορισμός `i − j ≤ Csep`). Αναλογία με VFH / Follow-the-Gap («valley» = συνεχόμενα ελεύθερα δείγματα). Η τιμή 5 είναι η default του upstream· το paper δεν δίνει αριθμό.==

#### β. Απότομη αλλαγή μήκους: `length_jump_threshold = 0.3 m`

$$
\left|L_{i_k} - L_{i_{k-1}}\right| > \texttt{length\_jump\_threshold}
$$

- Εντοπίζει απότομη αλλαγή του ελεύθερου μήκους ανάμεσα σε δύο γειτονικές αποδεκτές διαδρομές, ακόμα κι αν και οι δύο επαρκούν για φρενάρισμα. Ενεργεί μόνο στον dynamic.
-  **Ορίζεται πια στο `config/experiment.yaml`** (`dynamic_dwal.length_jump_threshold: 0.3`), όχι στο `evaluation.json`. Αλλάζει χωρίς build. Η παραλλαγή `dynamic_no_split` το απενεργοποιεί.
- Η σύγκριση γίνεται μόνο μεταξύ διαδοχικών αποδεκτών paths. Μια σταδιακή αλλαγή, π.χ. 1.0 → 1.2 → 1.4 → 1.6 m, μένει μία ομάδα.

### Πώς ερμηνεύεται το ιστόγραμμα

Φτιάχνουμε ιστόγραμμα των τιμών:

```
|ΔL|
```

Η υπόθεση είναι:

- μικρές τιμές `|ΔL|` → γειτονικά paths βλέπουν την ίδια επιφάνεια,
- μεγάλες τιμές `|ΔL|` → πιθανή άκρη εμποδίου ή ασυνέχεια ελεύθερου χώρου.

Ιδανικά το ιστόγραμμα έχει δύο περιοχές:

```
μικρές ΔL                  μεγάλες ΔL
ίδια επιφάνεια             πιθανό obstacle boundary
                                /\
                               /  \
____/\___________ ____________/    \____
                 τ
```

Το `τ` είναι το σημείο που χωρίζει τις δύο ομάδες.

#### Otsu

Ο Otsu δοκιμάζει όλα τα πιθανά thresholds και χωρίζει τα δεδομένα σε:

```
class 1: |ΔL| ≤ τ
class 2: |ΔL| > τ
```

Για κάθε `τ` υπολογίζει πόσο διαφορετικές είναι οι δύο ομάδες μεταξύ τους. Επιλέγει το threshold που μεγιστοποιεί τη μεταξύ-ομάδων διασπορά.

Άρα ο Otsu επιστρέφει:

```
τ_Otsu
```

Το οποίο είναι ένας στατιστικά φυσικός διαχωρισμός του ιστογράμματος.

Όμως ο Otsu δεν γνωρίζει αν το split είναι πραγματικά χρήσιμο για το DWAL. Ξέρει μόνο ότι χωρίζει καλά τις αριθμητικές τιμές.

#### GMM δύο συνιστωσών

Το GMM υποθέτει ότι τα δεδομένα αποτελούνται από δύο κατανομές:

```
μικρές ΔL ~ Gaussian 1
μεγάλες ΔL ~ Gaussian 2
```

Με EM εκτιμά:

```
π₁, μ₁, σ₁
π₂, μ₂, σ₂
```

Το threshold είναι το σημείο όπου οι δύο posterior πιθανότητες είναι ίσες:

```
P(class 1 | ΔL = τ)
=
P(class 2 | ΔL = τ)
```

ή ισοδύναμα:

```
π₁ N(τ; μ₁, σ₁)
=
π₂ N(τ; μ₂, σ₂)
```

Συνήθως παίρνουμε την τομή που βρίσκεται ανάμεσα στις δύο μέσες τιμές `μ₁` και `μ₂`.

Το αποτέλεσμα είναι:

```
τ_GMM
```

Ο GMM είναι χρήσιμος όταν οι δύο ομάδες έχουν διαφορετική διασπορά ή άνισο πλήθος δειγμάτων. Αν όμως το ιστόγραμμα είναι μονοτροπικό, το GMM μπορεί να επιβάλει τεχνητά δύο Gaussians. Γι’ αυτό πρέπει να καταγράφεται αν η διτροπικότητα είναι πραγματικά πειστική.

#### Πώς φτάνουμε στην «βέλτιστη» τιμή

Δεν θα έλεγα ότι η βέλτιστη τιμή είναι απλώς:

```
τ = τ_Otsu
```

ή:

```
τ = τ_GMM
```

Αυτά δίνουν υποψήφιες τιμές. Η τελική τιμή πρέπει να ελεγχθεί με τη συμπεριφορά των clusters.

Η σωστή διαδικασία είναι:

####  Στατιστικοί υποψήφιοι

Υπολογίζουμε:

```
τ_Otsu
τ_GMM
```

Παίρνουμε και επιπλέον τιμές σε ένα λογικό διάστημα:

```
κάτω όριο ≈ DS ή μερικά costmap cells
πάνω όριο ≈ πλάτος ρομπότ
```

Στο δικό σου σύστημα:

```
DS = 0.05 m
costmap resolution = 0.05 m
πλάτος iWalk ≈ 0.653 m
```

Άρα το `τ` δεν θα έπρεπε να είναι π.χ. `0.005 m`, γιατί αυτό είναι κάτω από την ανάλυση του συστήματος, ούτε πολύ μεγαλύτερο από το πλάτος του ρομπότ.


Δοκιμάζουμε αρκετές τιμές, για παράδειγμα:

```
0.05, 0.10, 0.15, 0.20, 0.25, 0.30, 0.35, ... , 0.65
```

Για κάθε threshold ξανατρέχουμε το clustering και μετράμε:

- πόσα clusters δημιουργούνται,
- πόσα paths μένουν μαζί ενώ έχουν διαφορετικό obstacle target,
- πόσα paths διασπώνται ενώ έχουν το ίδιο obstacle target,
- πόσο συχνά δημιουργούνται πολύ μικρά clusters,
- αν αυξάνονται τα oscillatory ή unstable cluster switches.

#### Αξιολόγηση under-splitting και over-splitting

Υπάρχουν δύο αντίθετα σφάλματα:

#### Πολύ μικρό threshold

Το threshold είναι υπερβολικά ευαίσθητο:

```
μικρός θόρυβος → νέο cluster
```

Αυτό προκαλεί:

- over-splitting,
- πολλά μικρά clusters,
- αστάθεια,
- πιθανό cluster flickering.

#### Πολύ μεγάλο threshold

Το threshold δεν κόβει πραγματικές ασυνέχειες:

- δύο διαφορετικά εμπόδια μένουν στο ίδιο cluster,
- το controller βλέπει ένα ψεύτικα συνεχές free-space region,
- γίνεται under-splitting.

Η βέλτιστη τιμή πρέπει να ισορροπεί αυτά τα δύο.

Μπορείς να το εκφράσεις ως objective:

```
Loss(τ) =
λ_under · under_split(τ)
+
λ_over · over_split(τ)
+
λ_small · tiny_clusters(τ)
+
λ_switch · cluster_instability(τ)
```

και να επιλέξεις το `τ` που ελαχιστοποιεί αυτό το loss.


 ==🔴**Γνωστή αδυναμία**: τοίχος υπό πολύ πλάγια γωνία (διάδρομος) δίνει μεγάλο ΔL χωρίς πραγματική άκρη εμποδίου, άρα ψευδές split. Μετριέται πια με το **over-split** (% συνεχόμενων paths με τον ίδιο «στόχο σύγκρουσης» που κόβονται σε ≥ 2 clusters), π.χ. στο `narrow_corridor`.==

##### «Μακριά 1 cluster, κοντά σπάει»: τεκμηρίωση χωρίς ground truth
- **Επιχείρημα**: φαινόμενο ορίζοντα. Όσο το εμπόδιο είναι έξω από τον ορίζοντα, το «αριστερά του» και το «δεξιά του» δεν διακρίνονται. Και ο original έχει διαφορετικό πλήθος clusters στο near (1.2) και στο far (1.8).
- ✅ Βιβλιογραφία: το TangentBug περιγράφει ακριβώς αυτό. Οι ασυνέχειες της range function (άκρες εμποδίων) εμφανίζονται μόνο εντός του εύρους του αισθητήρα.
- ✅ **Πότε είναι πρόβλημα**:
  - (α) **flicker**, split → merge → split. Μετριέται ως «αλλαγή πλήθους clusters που αναιρείται μέσα σε 0.5 s», ανά λεπτό.
  - (β) **απώλεια πίστης του estimator στο split**. Με την αντιστοίχιση `tracking` η πίστη του γονέα μοιράζεται στα παιδιά ανάλογα με την επικάλυψη (§ Correspondence). Μετριέται με τις μετρικές IDs.

| Paper | Πού στηρίζει | Τι παίρνουμε |
| --- | --- | --- |
| Kamon, Rimon, Rivlin, *TangentBug* (IJRR 1998) | Μηχανισμός Γ (άλμα μήκους), μαζί με το ND. Και το «μακριά ένα cluster, κοντά σπάει» | Οι **ασυνέχειες της range function** είναι άκρες εμποδίων και ορίζουν εναλλακτικές διαδρομές. Εμφανίζονται μόνο εντός του εύρους αισθητήρα, άρα πρόκειται για φαινόμενο ορίζοντα |

#### γ. Ελάχιστο πλάτος ομάδας: `min_cluster_span = 0.2 m`

Όταν μια ομάδα κλείνει, το πλάτος της υπολογίζεται ως χορδή στην ακτίνα αναφοράς $R = \texttt{levels.back()}$ (1.8 m και στους δύο τρόπους), ανάμεσα στην πρώτη και την τελευταία διαδρομή:

$$
w = \operatorname{chord}\left(R,\, \varphi(\kappa_{\mathrm{last}}, R) - \varphi(\kappa_{\mathrm{first}}, R)\right) = 2R\sin\frac{|\Delta\varphi|}{2}
$$

Η ομάδα κρατιέται αν και μόνο αν $w \ge \texttt{min\_cluster\_span}$. Αλλιώς απορρίπτεται ολόκληρη.

- Το πλάτος μετριέται στην ακτίνα $R$, όχι στο πραγματικό, κομμένο άκρο των διαδρομών.
- Μια ομάδα ενός path έχει $w = 0$, άρα απορρίπτεται.
- Το 0.2 m είναι **η τιμή του paper** (*«to avoid small clusters which could be the result of noise or could signify very tight spaces»*).
- ✅ **«Πρέπει να το κάνω σύμφωνα με τις διαστάσεις του iWalk;» Όχι.** Κάθε μέλος ελέγχεται ήδη με το **footprint** του iWalk, άρα το «χωράει το ρομπότ» ισχύει ανά path. Η χορδή μετρά πόσο **απλώνονται** οι ελεύθερες κατευθύνσεις στα 1.8 m, όχι το πλάτος του διαδρόμου. Αν τεθεί ίση με 0.653 m, το πλάτος θα μετρηθεί δύο φορές.

| Paper | Πού στηρίζει | Τι παίρνουμε |
| --- | --- | --- |
| Mujahed, Fischer, Mertsching, *Admissible Gap Navigation* (RAS 2018) | Μηχανισμός Δ (`min_cluster_span`) και ο ορισμός cluster | Ένα κενό είναι αποδεκτό όταν **περνιέται με εφικτή κίνηση** του συγκεκριμένου ρομπότ (σχήμα, κινηματική). Στον DWAL αυτό ισχύει ήδη ανά path: κινηματικά εφικτά τόξα, έλεγχος με footprint. Γι' αυτό η χορδή **δεν** τίθεται ίση με το πλάτος του ρομπότ |


## shared_controller node επιλογή cluster

**Fixed (upstream).** Δύο groups, near (1.2 m) και far (1.8 m). Η επιλογή group γίνεται με **hysteresis στη μετρημένη ταχύτητα**:
- από near σε far όταν `v > v_high = 0.28`,
- από far σε near όταν `v < v_low = 0.22`.

Τα defaults του upstream είναι 0.25/0.35. Με `max_linear = 0.3` το 0.35 δεν το φτάνει ποτέ, γι' αυτό άλλαξαν. Μέσα στο group, το cluster το επιλέγει ο estimator.

**Dynamic.** Ένα group (`clusters_far`, μεταβλητό μήκος έως 1.8 m), άρα δεν υπάρχει hysteresis. Πριν από τον estimator, ο controller:
- αφαιρεί από κάθε cluster όσα paths δεν δίνουν ταχύτητα προς τα εμπρός,
- στο semantic mode, αφαιρεί και όσα παραβιάζουν το `humanStopSafe`,
- ξαναϋπολογίζει το φ κάθε path στα 1.8 m, ώστε estimator και επιλογή να μετρούν στην ίδια ακτίνα.

**Estimator** (`dwal_intent_estimator.hpp`, υπάρχει μόνο στο repo, όχι στο paper). Σε κάθε κύκλο κρατά μια πιθανότητα (πίστη) για κάθε cluster ότι είναι αυτό που θέλει ο χρήστης, και την ενημερώνει σε δύο βήματα:
- **Πρόβλεψη (prior).** Η πίστη του προηγούμενου κύκλου μεταφέρεται στα τωρινά clusters. Ένα ποσοστό `alpha` (εμείς 0.92, default 0.8) πηγαίνει στο cluster με το **ίδιο ID** («η πρόθεση δεν άλλαξε», sticky prior). Το υπόλοιπο `1 − alpha` μοιράζεται στα άλλα με βάρος `exp(−β·|φ_C − φ_C,prev|)` (εμείς `β = 8`, default 2): όσο πιο κοντά γωνιακά, τόσο περισσότερο. Αν το ID χάθηκε, όλη η πίστη μοιράζεται έτσι.
- **Ενημέρωση (likelihood).** Η εντολή του χρήστη μετατρέπεται σε γωνία `φ_user = Kphi·ω` (`Kphi = 1.5`, με όριο). Κάθε cluster πολλαπλασιάζεται με μια ασύμμετρη Gauss γύρω από το `φ_C`, τη γωνία του path με το μικρότερο κόστος. Το εύρος είναι `eta = 0.5` φορές την απόσταση του `φ_C` από το αντίστοιχο άκρο του cluster, με ελάχιστο `sigma_min = 0.03 rad`.
- Επιλέγεται το cluster με τη μεγαλύτερη πίστη (MAP).
- Τι σημαίνουν οι τιμές μας: `alpha = 0.92` και `β = 8` κάνουν τον estimator πολύ «επίμονο». Χρειάζονται λίγοι κύκλοι με αντίθετη εντολή για να αλλάξει cluster, και σχεδόν όλη η υπόλοιπη πίστη πηγαίνει στο πιο κοντινό γωνιακά cluster. Τιμή που θα δικαιολογούσε το 0.92: π.χ. «η πρόθεση αλλάζει κατά μέσο όρο κάθε 1/(1−0.92) ≈ 12 κύκλους ≈ 0.6 s στα 20 Hz».
- **Με την αντιστοίχιση `tracking`** (`intent.split_by_overlap`, ενεργό μόνο τότε): το `alpha` ενός προηγούμενου cluster δεν πηγαίνει μόνο στο cluster με το ίδιο ID. Πηγαίνει σε όλα τα τωρινά clusters που επικαλύπτουν το γωνιακό του διάστημα (αφού διορθωθεί η στροφή του ρομπότ), ανάλογα με την επικάλυψη. Έτσι, σε split η πίστη του γονέα μοιράζεται στα παιδιά. Είναι δική μας επέκταση.

> ==🔴❓ **Ο Bayesian estimator δεν περιγράφεται στο paper.** Το paper (§5) περιγράφει FSM με scoring, timeout και persistence (soft/hard). Ο estimator υπάρχει μόνο στο repo. Οι τιμές μας (`intent.alpha = 0.92`, `beta = 8`, έναντι defaults 0.8/2) χρειάζονται τεκμηρίωση ή ρώτημα στον G. Moustris (§11, σημείο 9).==

> ==🔴Ερωτήσεις για τον υπεύθυνο / G. Moustris: (1)  Από πού προέρχονται τα `alpha = 0.92`, `β = 8`, `Kphi = 1.5`; (2) Συμφωνεί να κάνουμε ευαισθησία στο `alpha`/`β` (π.χ. alpha ∈ {0.8, 0.9, 0.95}, β ∈ {2, 4, 8}) με τις μετρικές επιλογής του SCAND;==
> Ευαισθησία alpha/β.
- alpha = πόση πίστη μένει στο ίδιο cluster από κύκλο σε κύκλο (πόσο «επίμονος» είναι ο estimator).
- β = πόσο προτιμά τα γωνιακά κοντινά clusters όταν η πίστη μετακινείται.
- Η ευαισθησία είναι να τρέξουμε το ίδιο SCAND με διάφορες τιμές τους (στο controllers/dwal.yaml, χωρίς build) και να δούμε πού το hit rate, το Brier και το log-loss είναι καλά και σταθερά.


## ==🔴shared_controller node επιλογή path==

Μέσα στο cluster που επέλεξε ο estimator:
1. `φ_near` = το μέλος με γωνία πιο κοντά στο `φ_user`.
2. Για κάθε μέλος: `J = (1−α)·c_norm + α·d_norm`, με `c_norm = cost/c_max`, `d_norm = |φ − φ_near| / φ_span` και `α = 0.7` (upstream `scoreJ`). Επιλέγεται το μικρότερο J: κοντά σε ό,τι ζητά ο χρήστης, με προτίμηση σε φθηνότερα (πιο μακριά από εμπόδια) paths.
3. Στο semantic mode: `J = (1−w)·J + w·social`, με `social = exp(−d²/2σ²)`, όπου d η μικρότερη απόσταση path–άνθρωπος σε προβλεπόμενο χρόνο, `σ = personal_space = 0.8 m` και `w = 0.35`.

**Fixed και dynamic**: ο ίδιος κανόνας. Διαφέρει μόνο η σημασία του κόστους: στον fixed είναι το μέγιστο ως το R του level, στον dynamic σε όλο το ελεύθερο μήκος.

## ==🔴shared_controller node υπολογισμός v, ω==

**Fixed (upstream, αμετάβλητο).**
- `v = v_user · max(s_min, 1 − c*/c_max)`, όπου c* το κόστος του path που επιλέχθηκε (`s_min = 0.2`, `c_max = 255`).
- `ω = v · k*`.
- Αν `|v| < 1e-3`: `ω = ω_user` (περιστροφή επί τόπου).
- Αν `v_user < 0`: η εντολή περνά αυτούσια (συμπεριφορά upstream). Υποθέτουμε ότι εντολή όπισθεν δεν έρχεται στα πειράματα. Αν έρθει, ο smoother την κόβει στο 0 (`min_velocity` γραμμικής = 0).

**Dynamic** (`candidateSpeed`), για κάθε path:
1. Η εντολή όπισθεν αγνοείται: `v_user ← max(0, v_user)`, και η περιστροφή κρατιέται.
2. `room = min(L − m, π/(2|κ|))`: το φρενάρισμα πρέπει να χωρά στο ελεύθερο μήκος και στο τόξο πριν την ευθεία.
3. `v_cap = √(a²T² + 2a·room) − aT`, από τη λύση της `vT + v²/2a ≤ room`.
4. `v = min(v_user, v_max, v_cap, ω_max/|κ|, [semantic: a(H−T)])`.
5. **Χωρίς όρο κόστους**: δεν υπάρχει πια πολλαπλασιαστής `max(s_min, 1 − c/c_max)` (§ Αργή κίνηση).
6. **Χωρίς απόρριψη**: η αποδοχή του path κρίνεται μόνο στο clustering (§ braking_requirement). Εδώ υπολογίζεται μόνο η ταχύτητα.
7. `ω = v · κ*` του path που επιλέχθηκε.

| L | v_cap (a = 0.5, T = 0.4, m = 0.05) |
|---|---|
| 0.30 m | 0.34 m/s |
| 0.15 m | 0.17 m/s |
| 0.10 m | 0.10 m/s |

## Velocity smoother

Κόμβος `nav2_velocity_smoother` (`dwal_cafe.launch.py`), **`/cmd_vel_selected` → `/cmd_vel_smoothed`**.
- Παράμετροι από το `prepare_scene.py`: `max_velocity`, `min_velocity`, `max_accel` και `max_decel` (0.5 m/s², γωνιακά 1.0 rad/s²), `velocity_timeout 0.3 s`, 20 Hz, OPEN_LOOP.
- Δεν αλλάζει διαδρομή. Αλλάζει μόνο το πόσο απότομα εφαρμόζεται η εντολή (απότομο command → ομαλό command).

**Γιατί χρειάζεται**
1. **Το Gazebo `planar_move` είναι ιδανικό**: εφαρμόζει την εντολή ακαριαία, με άπειρη επιτάχυνση. Το DWA του generator (`acc_lim = 0.5`) και το μοντέλο πέδησης (`a = 0.5`) υποθέτουν πεπερασμένη επιτάχυνση.
   - Χωρίς smoother, το προσομοιωμένο ρομπότ είναι πιο ευέλικτο από το μοντέλο και από το πραγματικό iWalk.
   - Τα αποτελέσματα θα έβγαιναν αισιόδοξα, π.χ. σε ομαλότητα και σε ακαριαία στάση.
   - Ο smoother κάνει την προσομοίωση να ταιριάζει με το μοντέλο (`|Δv| ≤ a·Δt`).
2. **Η έξοδος του controller δεν φράσσεται σε επιτάχυνση.** Η ταχύτητα αλλάζει απότομα όταν αλλάζει το path. 📊 Στο `/cmd_vel_selected`, `|dv/dt|` έως 1.1–1.3 m/s², αν και σπάνια (0.2–0.6 % των δειγμάτων) σε αργά runs. Το dynamic window δεν το εμποδίζει, γιατί περιορίζει μόνο το εύρος καμπυλοτήτων.
3. Χωρίς smoother, η επιβράδυνση 0.5 του μοντέλου πέδησης δεν θα αντιστοιχούσε στη συμπεριφορά του ρομπότ.
4. Κόβει την αρνητική γραμμική ταχύτητα στο 0 (`min_velocity`).

- Χρησιμοποιεί `/scan`, το footprint, TF και forward simulation της κίνησης.
- Ζώνη `FootprintApproach`, `action_type: approach`, `simulation_time_step: 0.05`.
- Αν το ρομπότ, συνεχίζοντας με την τρέχουσα εντολή, θα πλησίαζε εμπόδιο σε λιγότερο από `time_before_collision`, μειώνει την ταχύτητα ώστε `v ≤ d / time_before_collision`.
- Διαφορά από τον DWAL: ο DWAL επιλέγει path πριν παραχθεί η εντολή. Ο collision monitor κάνει τελικό, ανεξάρτητο έλεγχο πάνω στην ταχύτητα που ήδη παράχθηκε.

**Γιατί χρειάζεται:**
1. **Είναι ο μόνος έλεγχος της περιστροφής επί τόπου.**
   - Όταν δεν υπάρχει αποδεκτή κίνηση προς τα εμπρός, ο dynamic δίνει `v = 0` με το ω του χρήστη.
   - Με `|v_user| < 1e-3` περνά περιστροφή (`inplace_via_collision_monitor: true`). Ο κώδικας **απαιτεί** collision monitor.
   - Το footprint του iWalk είναι ασύμμετρο (μπροστά 0.865 m, πίσω 0.103 m). Η περιστροφή σαρώνει κύκλο ακτίνας περίπου `√(0.865² + 0.327²) ≈ 0.92 m`, ενώ ο DWAL ελέγχει μόνο τόξα προς τα εμπρός.
2. **Ο fixed (upstream)** περνά περιστροφή χωρίς έλεγχο.
3. **Ανεξάρτητη πηγή**: δουλεύει πάνω στο raw scan (15 Hz), άρα καλύπτει την καθυστέρηση costmap + generator.

✅ **`time_before_collision` από το ίδιο μοντέλο πέδησης** (υλοποιήθηκε, `prepare_scene.py`):

$$
t_{bc} = T + \frac{v_{max}}{2a} = 0.4 + \frac{0.3}{2\cdot 0.5} = 0.7\ \mathrm{s}
$$

- Προηγουμένως ήταν 1.2 s, γραμμένο με το χέρι.
- Το `approach` επιβάλλει `v·t_bc ≤ d`. Το DWAL ζητά `vT + v²/(2a) ≤ d` (χωρίς το περιθώριο m).
- Για κάθε `v ≤ v_max`: `v·t_bc = vT + v·v_max/(2a) ≥ vT + v²/(2a)`, με ισότητα στο `v_max`. Άρα ο collision monitor δεν είναι ποτέ πιο ελαστικός από όσο χρειάζεται το μοντέλο, και στο `v_max` συμπίπτει μαζί του.
- Με 1.2 s ήταν 70 % αυστηρότερος. Στα 0.3 m/s ζητούσε 0.36 m αντί για 0.21 m, δηλαδή ένα δεύτερο, ασύμβατο μοντέλο πέδησης.
- Αλλάζει αυτόματα αν αλλάξουν τα T, a ή `max_linear`.

- Μέσω του v_cap: όσο μικρότερο το ελεύθερο μήκος, τόσο μικρότερη η ταχύτητα. Π.χ. 0.10 m ελεύθερα → 0.10 m/s.

- Μέσω του ορίου της γωνιακής ταχύτητας.
- Το κόστος δεν μειώνει πια την ταχύτητα. Επηρεάζει μόνο ποιο path επιλέγεται (απόσταση από εμπόδια).
- Ο fixed έμεινε όπως ήταν.

📊 **Μέτρηση** (dense_static, seed 1, πριν από τις αλλαγές). Μέση εντολή στην είσοδο 0.146 m/s, στην έξοδο του controller 0.033 m/s. Smoother και collision monitor **δεν έκοψαν τίποτα**: όλη η επιβράδυνση γινόταν στον controller.

**Αιτία: ο όρος κόστους.** Στον dynamic, το κόστος ενός path είναι το μέγιστο κόστος footprint **ως το σημείο σύγκρουσης**. Το τελευταίο ελεύθερο σημείο ακουμπά πάντα το inflation του εμποδίου (κόστος κοντά στο 252). Άρα:

| Ελεύθερο μήκος L | Paths με συντελεστή στο s_min = 0.2 | Όριο πέδησης `min(v_cap, 0.3)` |
|---|---|---|
| < 0.5 m | **100 %** | 0.20 |
| 0.5–1.0 m | **100 %** | 0.30 (δεν περιορίζει) |
| 1.0–1.5 m | **100 %** | 0.30 |
| ≥ 1.5 m | 71 % | 0.30 |

Ένα path ελεύθερο για 1.4 m κινούνταν με 20 % της ταχύτητας, ενώ το όριο πέδησης επέτρεπε 100 %.

✅ **Απόφαση (υλοποιήθηκε): ο όρος κόστους αφαιρείται από την ταχύτητα του dynamic.**
- Στον dynamic, η απόσταση από το εμπόδιο μετριέται ήδη από το `v_cap`: ταχύτητα με την οποία το ρομπότ σταματά μέσα στο ελεύθερο μήκος. Αυτή είναι η συνθήκη admissible του DWA.
- Ο πολλαπλασιαστής `max(s_min, 1 − c/c_max)` μετρούσε την ίδια ποσότητα **δεύτερη φορά**, και μάλιστα χωρίς φυσική μονάδα (κόστος inflation αντί για μέτρα).
- Στο DWA (Fox 1997) η απόσταση από εμπόδια μπαίνει (α) στο **admissibility** (ποιες ταχύτητες επιτρέπονται) και (β) στη **συνάρτηση επιλογής** (όρος `dist`). Δεν μπαίνει ως πολλαπλασιαστής της ταχύτητας.
- Εμείς κρατάμε και τα δύο: (α) με το `v_cap` και το φίλτρο του clustering, (β) με τον όρο `c_norm` στο `J` της επιλογής path.
- Στο paper του DWAL το κόστος χρησιμοποιείται για να επιλεγεί path με απόσταση από εμπόδια (*«ensures a minimum clearance of the path»*), όχι για να μειωθεί η ταχύτητα. Ο πολλαπλασιαστής ταχύτητας υπάρχει μόνο στον κώδικα του upstream, όπου το κόστος μετριέται ως το σταθερό R. Ο fixed τον κρατά αμετάβλητο.
- Τα `s_min`, `inflation_radius`, `cost_scaling_factor` **δεν** αλλάζουν. Επηρεάζουν πια μόνο τον fixed και την επιλογή path.

| Σημείο | Τι ισχύει τώρα | Τεκμηρίωση |
| --- | --- | --- |
| Όρος κόστους (dynamic) | αφαιρέθηκε από την ταχύτητα, μένει στην επιλογή path | βλ. παραπάνω |
| Όρος κόστους (fixed) | αμετάβλητος (upstream) | baseline |
| Όριο πέδησης `v_cap` | μένει | DWA admissibility |
| «Μετρημένη ταχύτητα > όριο → απόρριψη» | μόνο στο clustering (§ braking_requirement) | μία πηγή αλήθειας |
| Collision monitor | `t_bc = T + v_max/(2a) = 0.7 s` | § Collision monitor |
| Speed limit | αφαιρέθηκε (ήταν σταθερό 0.3 = `max_linear`) | § Command guard |

Πώς βλέπεις πού χάνεται η ταχύτητα: το `metrics_summary.py` δείχνει πια τη μέση ταχύτητα σε κάθε στάδιο (reference → selected → smoothed → safe → final), στον πίνακα «Αλυσίδα εντολών».


### braking_requirement
✅ **Πού υλοποιείται η λογική του dynamic window στον DWAL.** Κατά τους Fox, Burgard, Thrun (1997), ο χώρος αναζήτησης είναι η **τομή** `V_r = V_s ∩ V_a ∩ V_d`:
- `V_a` (admissible): `v ≤ √(2·dist(v,ω)·v̇_b)`, δηλαδή το ρομπότ προλαβαίνει να σταματήσει πριν από το εμπόδιο.
- `V_d` (dynamic window): ταχύτητες εφικτές μέσα στον επόμενο κύκλο, με πεπερασμένη επιτάχυνση.

Επειδή είναι τομή, η σειρά δεν παίζει ρόλο: «πρώτα admissible και μετά window» δίνει το ίδιο με το αντίστροφο. Χρειάζονται και τα δύο, γιατί απαντούν σε διαφορετικά ερωτήματα (ασφάλεια, εφικτότητα).

| Σκέλος DWA | Fixed | Dynamic |
|---|---|---|
| `V_s` | όρια v, ω | όρια v, ω |
| `V_d` | **generator** (εύρος καμπυλοτήτων από το window) | ίδιο |
| `V_a` | **έμμεσα**: σταθερό R (1.2 m ↔ πέδηση από 0.89 m/s, 1.8 m ↔ από 1.14 m/s) | **clustering**: `min(L, m + π/(2|κ|)) ≥ S_req(v_μετρ.)` |
Ο fixed έχει admissible velocities; Όχι ρητά.
- Δέχεται μόνο paths ελεύθερα ως τα 1.2/1.8 m. Αυτό αρκεί για φρενάρισμα από 0.89/1.14 m/s, πολύ πάνω από το 0.3, άρα το admissible ισχύει έμμεσα και υπερβολικά συντηρητικά.
- Το dynamic window του generator υπάρχει και στους δύο.

✅ **«Μήπως το admissible υλοποιείται ήδη σε προηγούμενο βήμα;»** Όχι. Ο generator υλοποιεί μόνο το `V_d`. Το admissible υλοποιούνταν **δύο φορές, μετά** τον generator:
- στο clustering (ως προς L: ποιο μήκος χρειάζεται με την τρέχουσα v),
- στον controller (ως προς v: απόρριψη αν `v_μετρ. > v_cap(L)`).

✅ **Είναι το φίλτρο στο clustering περιττό;**
1. **Λογικά, για την τελική αποδοχή, ήταν διπλό με τον controller.** Το `S_req(v) = vT + v²/2a + m` είναι γνησίως αύξον, άρα `L ≥ S_req(v) ⇔ v ≤ v_cap(L)`. Κάθε path που έκοβε το clustering θα το έκοβε και ο controller.
2. **Για τη δομή των clusters δεν είναι περιττό.** Τα paths που κόβει δημιουργούν κενά δεικτών (splits), αλλάζουν τα «γειτονικά» για το άλμα μήκους και το πλάτος `w`. Χωρίς αυτό, τα clusters θα είχαν μέλη που ο controller πετά αργότερα: «κούφια» clusters με λάθος `φ_C` για τον estimator.
3. **Πρακτικά, απορρίπτει.** 📊 Στο dynamic run: 8.8 % των paths με κωδικό −2, τουλάχιστον μία απόρριψη σε 48 % των frames, διάμεσο `required_length` 0.063 m. Η υπόθεση «δεν απορρίπτει ποτέ» **διαψεύδεται**, οπότε δεν μπορεί να σβηστεί με αυτό το επιχείρημα.

✅ **Απόφαση (υλοποιήθηκε): μία πηγή αλήθειας στο clustering.**
- Το φίλτρο του clustering παίρνει και το όριο τόξου: δεκτό αν `min(L, m + π/(2|κ|)) ≥ S_req(v)`.
- Το heartbeat `/dwal_planner/braking_requirement` μεταφέρει γι' αυτό και το `m` (4 τιμές: `[S_req, timeout, stamp, m]`).
- Ο controller δεν απορρίπτει πια paths λόγω πέδησης. Υπολογίζει μόνο την ταχύτητα `v_cap` (§ υπολογισμός v, ω).

**Σύγκριση με τον τύπο του paper:**

| Όρος | Fox 1997 | Εμείς | Γιατί |
|---|---|---|---|
| Πέδηση | `v²/2v̇_b` | `v²/2a` | ίδιο |
| Αντίδραση | — | `vT` | καθυστέρηση αισθητήρα–costmap–generator–pipeline. Δομή απόστασης διαχωρισμού όπως στο ISO/TS 15066 (μόνο η δομή) |
| Περιθώριο | — | `m = 0.05` | να μη σταματήσει πάνω στο εμπόδιο |
| `dist(v,ω)` | απόσταση πάνω στο τόξο | `available_length` (με footprint) | ίδια έννοια |
| Όριο τόξου | — | `L ≤ m + π/(2|κ|)` | το path γίνεται ευθεία μετά τις 90°, ενώ το φρενάρισμα υποτίθεται σε σταθερή καμπυλότητα |
| Όριο ω | `ω ≤ √(2·dist·ω̇_b)` | `v ≤ ω_max/|κ|` | σταθερή καμπυλότητα: το ω μηδενίζεται μαζί με το v |

Με `T = 0` και `m = 0` δίνει ακριβώς `√(2aL)`.

### ==🔴Clustering Correspondance (αντιστοίχιση IDs μεταξύ frames)==
#### Τι κάνει ο original
1. Αντιπρόσωπος κάθε cluster = μέση γωνία των άκρων.
2. Πίνακας `|φ̄_prev − φ̄_cur|`.
3. Greedy: min(prev, cur) φορές βρίσκει το καθολικό ελάχιστο, αναθέτει το ID και σβήνει γραμμή και στήλη.
4. Χωρίς gating, με μνήμη 1 frame. Τα νέα παίρνουν «το μικρότερο ελεύθερο ID» (fixed με B2).

**Γιατί το greedy αποτυγχάνει**:
- Προηγούμενα A (φ = 0) και B (φ = 1). Τωρινά X (φ = 0.55) και Y (φ = 1.60).
- Greedy: B→X (0.45), μετά αναγκαστικά A→Y (1.60). Σύνολο 2.05, και η σειρά **αντιστρέφεται**, κάτι αδύνατο για περάσματα.
- Βέλτιστο: A→X και B→Y. Σύνολο 1.15, με τη σειρά να διατηρείται.

==🔴**Πρόταση (μόνο dynamic)**==:

✅ **Υλοποιήθηκε ως δεύτερος τρόπος, που επιλέγεται από yaml** (`config/experiment.yaml`, χωρίς build):
```yaml
dynamic_dwal:
  correspondence: upstream     # upstream | tracking
  correspondence_gate: 0.2     # tracking: ελάχιστο IoU για κληρονομιά ID
  track_keep_frames: 2         # tracking: πόσα frames κρατιέται ID που χάθηκε (2 = 0.4 s στα 5 Hz)
```
- `upstream`: το greedy του original, με το B2 διορθωμένο. Είναι το default, ώστε να μείνουν συγκρίσιμα τα παλιά αποτελέσματα.
- `tracking`: τα βήματα 1–6:

| Βήμα | Τι | Από πού |
| --- | --- | --- |
| 1 | Ομοιότητα = **interval IoU** των γωνιακών διαστημάτων στα 1.8 m: `J = |I1 ∩ I2| / |I1 ∪ I2|`. **Όχι** σύνολα καμπυλοτήτων, γιατί το πλέγμα μετακινείται | Jaccard 1912 |
| 2 | Βέλτιστη ανάθεση με διατήρηση σειράς (δυναμικός προγραμματισμός, όπως στη στοίχιση ακολουθιών), με μέγιστο συνολικό IoU. Αφού τα περάσματα δεν μπορούν να διασταυρωθούν, είναι το βέλτιστο του Hungarian περιορισμένο σε αναθέσεις χωρίς διασταύρωση | Kuhn 1955, Munkres 1957 |
| 3 | Gating: αν `J < 0.2`, νέο ID αντί για κληρονομιά | Blackman & Popoli 1999 |
| 4 | Track management: ID που χάθηκε κρατιέται 2 frames (0.4 s), και τα IDs δεν ξαναχρησιμοποιούνται | Blackman & Popoli 1999 |
| 5 | Split/merge: το ID το κληρονομεί το παιδί με το μεγαλύτερο IoU (βήμα 2). Η πίστη του γονέα μοιράζεται σε όλα τα παιδιά ανάλογα με την επικάλυψη (στον estimator, `intent.split_by_overlap`) | **Δική μας επέκταση** |
| 6 | Αντιστάθμιση ego-motion: τα προηγούμενα διαστήματα στρέφονται κατά −Δθ πριν από τη σύγκριση | Γεωμετρία |

Σημείωση υλοποίησης: το μήνυμα `PathCluster` **δεν άλλαξε**. Μια πρώτη εκδοχή πρόσθετε πεδία «γονέων», αλλά τότε τα παλιά bags δεν διαβάζονταν πια. Το βήμα 5 γίνεται λοιπόν στον estimator, από τα γωνιακά διαστήματα δύο διαδοχικών frames.

**Μέτρο ομοιότητας**:
$$J(C_1,C_2)=\frac{\lvert[\phi^1_{min},\phi^1_{max}]\cap[\phi^2_{min},\phi^2_{max}]\rvert}{\lvert[\phi^1_{min},\phi^1_{max}]\cup[\phi^2_{min},\phi^2_{max}]\rvert}$$
Ισούται με 1 όταν τα διαστήματα ταυτίζονται και με 0 όταν δεν επικαλύπτονται. Είναι καλύτερο από τη μέση γωνία: αν ένα cluster μεγαλώσει από τη μία πλευρά, η μέση γωνία του μετακινείται, ενώ η επικάλυψη μένει μεγάλη.

✅ **Gating («πύλη»).** Δεν είναι το ίδιο με τα *freshness gates* του controller. Εκείνα ελέγχουν αν μια **είσοδος** (odometry, εντολή, clusters) είναι αρκετά πρόσφατη, π.χ. odometry ≤ 0.5 s, αλλιώς σταματούν το ρομπότ. Το gating εδώ ελέγχει, πριν δοθεί κληρονομικά ένα ID, ότι η αντιστοίχιση είναι αρκετά καλή (`J ≥ 0.2`). Αν όχι, το cluster παίρνει **νέο** ID.

Παράδειγμα: ένα cluster εξαφανίζεται αριστερά και την ίδια στιγμή εμφανίζεται ένα δεξιά. Ο upstream δίνει στο δεξί το ID του αριστερού, και ο estimator μεταφέρει το 92 % της πίστης σε τελείως άλλη κατεύθυνση. Με gating το δεξί είναι νέο, και η πίστη του αριστερού μοιράζεται ανάλογα με την εγγύτητα. Επαληθεύτηκε σε συνθετική ακολουθία: upstream `[2] → [2]` (κληρονομιά), tracking `[2] → [3]`.

**Track management**:
- Ένα ID που χάθηκε κρατιέται για 2 frames. Αν το cluster ξαναεμφανιστεί (π.χ. χάθηκε για ένα frame από θόρυβο στο costmap), παίρνει πίσω το ίδιο ID.
- **Τα IDs δεν ξαναχρησιμοποιούνται.** Ο upstream δίνει «το μικρότερο ελεύθερο», οπότε το ID 0 μπορεί να σημαίνει διαφορετικό πέρασμα σε διαφορετικές στιγμές.

**Ego-motion**: όταν το ρομπότ στρίβει κατά Δθ ανάμεσα σε δύο frames, όλα τα clusters μετακινούνται κατά −Δθ στη γωνία φ, γιατί το φ μετριέται ως προς το ρομπότ. Με 0.8 rad/s και 5 Hz, Δθ = 0.16 rad ≈ 9°, συγκρίσιμο με πλάτος cluster.

✅ **«Μήπως να κάνω τεστ με greedy και με την πρόταση και να συγκρίνω μετρικές;»** Ναι, με δύο τρόπους:
- **Offline**: το `evaluation.py` ξανατρέχει και τους δύο τρόπους πάνω στα clusters κάθε bag (ίδια είσοδος) και δίνει ID switches, fragmentations, crossings, διπλά IDs και αστήρικτη κληρονομιά. Πίνακας «Συνέπεια IDs».
- **Online**: `correspondence: tracking` στο yaml, και σύγκριση των runs με τις μετρικές επιλογής.


### μοντέλο φρεναρίσματος στο humanStopSafe (μόνο σε semantic mode)

Τα βήματα, για κάθε υποψήφιο path:
1. Χρόνος ως τη στάση: ${stop\_time} = T + v/a_{brake}$, με v τη μεγαλύτερη από τη μετρημένη και την ταχύτητα που θα δοθεί. Αν ξεπερνά τον ορίζοντα πρόβλεψης `H = 2 s`, το path απορρίπτεται.
2. Προσομοίωση του φρεναρίσματος σε βήματα των 25 ms. Για $t < T$ το ρομπότ κινείται με σταθερή ταχύτητα, μετά επιβραδύνει: $s = v·t − ½·a·(t−T)²$. Θέση και προσανατολισμός πάνω στο τόξο καμπυλότητας κ.
3. Πρόβλεψη ανθρώπων με σταθερή ταχύτητα: $p_h(t) = p_{μέτρησης} + v_h·(track\_age + t)$.
4. Απόρριψη αν ο άνθρωπος είναι μέσα στο footprint ή πιο κοντά από `r_h + u + g·t + dt·(|v_h| + v·(1 + R_fp·|κ|))`.
5. `track_age > 0.5 s` σημαίνει απόρριψη. Επιτρέπεται απόκλιση ρολογιών έως −0.1 s, και τότε `track_age = 0`.

Διευκρινίσεις:
- **Ηλικία μέτρησης (`track_age`)** = τώρα − stamp του μηνύματος tracks. Παράδειγμα: άνθρωπος με 1 m/s, μέτρηση πριν από 0.1 s, θέση σε t = 0.5 s: μετακίνηση 1 · (0.1 + 0.5) = 0.6 m.
- **Growth (`human_uncertainty_growth`, 0.1 m/s)**: η πρόβλεψη σταθερής ταχύτητας χαλά όσο κοιτάμε πιο μακριά (ο άνθρωπος μπορεί να στρίψει ή να σταματήσει). Γι' αυτό ο κύκλος γύρω του μεγαλώνει: 0.5 m στο t = 0, 0.6 m στο t = 1 s, 0.7 m στο t = 2 s.
- **Όρος δειγματοληψίας**: η μέγιστη απόσταση που διανύουν άνθρωπος και ρομπότ σε ένα βήμα των 25 ms, μαζί με την περιστροφή του footprint, ώστε να μη «χαθεί» επαφή ανάμεσα στα δείγματα.

## ✅ Ετικέτες «στόχου σύγκρουσης»: τι είναι και γιατί

**Το πρόβλημα.** Για να κρίνουμε αν ένα cluster είναι «σωστό», χρειαζόμαστε μια αναφορά για το ποια paths είναι **η ίδια επιλογή κίνησης**. Ground truth γι' αυτό δεν υπάρχει, ούτε στο HuNav ούτε στο SCAND.

**Η ιδέα.** Δύο paths είναι η ίδια επιλογή όταν καταλήγουν στο **ίδιο πράγμα**:
- Για κάθε path που μπήκε σε cluster, βρίσκουμε σε ποιο εμπόδιο σταματά. Εμπόδιο = συνεκτική ομάδα lethal κελιών του costmap. Το εμπόδιο του path είναι αυτό που βρίσκεται πιο κοντά στο footprint του iWalk στην τελευταία ελεύθερη θέση.
- Αν το path φτάνει τον ορίζοντα χωρίς να σταματήσει, η ετικέτα είναι «ελεύθερο».
- Paths που καταλήγουν στο ίδιο εμπόδιο (ή είναι όλα ελεύθερα) = ίδια επιλογή. Paths που καταλήγουν σε διαφορετικά εμπόδια, ή το ένα περνά και το άλλο σταματά = διαφορετικές επιλογές, π.χ. «προς τον άνθρωπο» έναντι «δίπλα του».

**Γιατί το θέλουμε.** Είναι η πιο άμεση τεκμηρίωση του split (μηχανισμός Γ) χωρίς ground truth:
- **mixed** = % clusters που περιέχουν paths με ≥ 2 ετικέτες. Το split πρέπει να το **μειώνει**.
- **over-split** = % συνεχόμενων paths με την ίδια ετικέτα που κόβονται σε ≥ 2 clusters. Ένα πολύ «επιθετικό» κατώφλι το **αυξάνει**.
- Η σάρωση του `length_jump_threshold` δείχνει πού ισορροπούν τα δύο. Υπολογίζονται μόνο από το costmap του bag.

**Περιορισμός**: αντικείμενα που ακουμπούν (π.χ. άνθρωπος δίπλα σε τοίχο) γίνονται μία συνιστώσα, άρα μία ετικέτα.

## SCAND πειράματα
**Γιατί το SCAND βοηθά στο clustering**: είναι **open loop**, το ρομπότ ακολουθεί την καταγεγραμμένη πορεία. Όλες οι παραλλαγές βλέπουν λοιπόν **ακριβώς** τα ίδια costmaps και την ίδια odometry: ίδια είσοδος, διαφορετικός αλγόριθμος.

✅ **Οι μετρικές ασφάλειας δεν υπολογίζονται στο SCAND**: συγκρούσεις, personal zone, απόσταση από ανθρώπους/εμπόδια, απόσταση της πρότασης από εμπόδια. Η θέση είναι η ηχογράφηση του Jackal (έως ~2 m/s), ενώ ο controller βλέπει ταχύτητα σε κλίμακα iWalk (0.3 m/s). Φρενάρισμα και αποστάσεις δεν περιγράφουν λοιπόν εφικτή κίνηση του iWalk. Το `metrics.json` γράφει την εξήγηση (`safety_metrics`), και ο πίνακας του `metrics_summary.py` τη δείχνει με «— ‡» και υποσημείωση. Στο SCAND έχουν νόημα μόνο οι μετρικές clustering, αντιστοίχισης και επιλογής.

✅ **Baseline «μόνο χρήστης»**: ένας αφελής «προβλέπτης» που υποθέτει ότι ο χρήστης θα συνεχίσει με την **τωρινή** καμπυλότητα `κ = ω/v` της εντολής του. Συγκρίνουμε με την πραγματική μελλοντική διαδρομή και την επιλογή του controller και αυτό το τόξο.
- Στο SCAND η «εντολή χρήστη» είναι η ταχύτητα που εκτελέστηκε, άρα ήδη μοιάζει πολύ με το μέλλον. Σε ανοιχτό χώρο το baseline είναι δύσκολο να νικηθεί.
- Ο controller πρέπει να δείξει ότι **προσθέτει αξία κοντά σε εμπόδια**. Γι' αυτό τα αποτελέσματα χωρίζονται και ανά απόσταση από εμπόδιο (`by_obstacle_distance`: < 1 m, 1–2 m, > 2 m).

✅ **Εξαιρέσεις**: το Jackal είναι μικρότερο από το iWalk (περίπου 0.51 × 0.43 m έναντι footprint 0.97 × 0.65 m). Η πραγματική διαδρομή του μπορεί να περνά από σημεία όπου το iWalk **δεν χωρά**.
- Σε αυτά τα frames το «σωστό» δεν είναι εφικτό για τον controller. Δεν το προτείνει, αλλά δεν φταίει.
- Τα frames αυτά εντοπίζονται (footprint του iWalk πάνω στη μελλοντική διαδρομή απέναντι στα σημεία του scan) και αναφέρονται χωριστά. Ο πίνακας δείχνει τα εφικτά frames και το ποσοστό εξαιρέσεων.

Το SCAND καταγράφει πια επιπλέον το costmap και το `/shared_controller/intent_diagnostics`, που χρειάζονται για τα παραπάνω.

## Στατιστικά
Υλοποιήθηκαν στο `metrics_summary.py`, ενότητα «Στατιστική». Τα runs ζευγαρώνονται με ίδιο σενάριο, seed και semantics. Συγκρίσεις: fixed έναντι dynamic_split, dynamic_no_split έναντι dynamic_split.
- **Wilcoxon signed-rank** (Wilcoxon 1945): έλεγχος για **ζευγαρωτές** μετρήσεις.
    - Παίρνει τις διαφορές κάθε ζεύγους, τις κατατάσσει κατ' απόλυτη τιμή, και ελέγχει αν οι θετικές «βαραίνουν» περισσότερο από τις αρνητικές.
    - Δεν υποθέτει κανονική κατανομή, κάτι χρήσιμο με λίγα seeds.
    - Δίνει p-value: πόσο πιθανή θα ήταν η διαφορά αν δεν υπήρχε πραγματική επίδραση. Υπολογίζεται ακριβώς, όχι με προσέγγιση.
    - Με λιγότερα από 6 ζεύγη δεν μπορεί να βγει p < 0.05 (με 5 ζεύγη το μικρότερο δυνατό είναι 0.0625).
- **Μέγεθος επίδρασης**: πόσο **μεγάλη** είναι η διαφορά, ανεξάρτητα από το αν είναι «στατιστικά σημαντική».
    - Matched-pairs rank-biserial correlation, από −1 έως 1. +1 σημαίνει ότι όλα τα ζεύγη πάνε προς την ίδια θετική κατεύθυνση.
    - Δίνεται και η διάμεση διαφορά σε φυσικές μονάδες (π.χ. «−3.2 s standstill»).
- **Bootstrap 95 % CI** (Efron 1979): διάστημα εμπιστοσύνης χωρίς τύπους.
    - Ξαναδιαλέγουμε τυχαία, με επανάθεση, ζεύγη από τα δεδομένα 10 000 φορές, και υπολογίζουμε κάθε φορά τη διάμεση διαφορά.
    - Το διάστημα από το 2.5 % ως το 97.5 % αυτών των τιμών είναι το 95 % CI. Αν δεν περιέχει το 0, η διαφορά είναι αξιόπιστη.

## Επίπεδο 1: r σταθερό → μεταβλητό

- HuNav: ακινησία ενώ ζητείται κίνηση, μαζί με συγκρούσεις (εμπόδιο/άνθρωπος), ελάχιστη απόσταση από ανθρώπους και εμπόδια, χρόνο και path σε προσωπική ζώνη, ομαλότητα.
- SCAND: κωδικοί διάγνωσης (−2 φρενάρισμα, μηνύματα χωρίς cluster) και ψευδή stops.

✅ **Τι εννοούσα με τη «Στατιστική» στο «Διευκρινήσεις μετά το meeting 2710»**: κάθε σενάριο τρέχει με το ίδιο seed μία φορά με fixed και μία με dynamic. Η μονάδα σύγκρισης είναι το **ζεύγος** (ίδιο seed). Πάνω στις διαφορές των ζευγών εφαρμόζονται Wilcoxon, μέγεθος επίδρασης και bootstrap CI, όπως εξηγούνται παραπάνω.

## Επίπεδο 2: clustering

**Μετρικές** (✅ όλες υλοποιημένες, πίνακες «Clustering χωρίς ground truth» και «Συνέπεια IDs»):
1. **Flicker** (αλλαγή πλήθους που αναιρείται σε < 0.5 s) και αλλαγές πλήθους ανά λεπτό.
2. **Clustering stability**: ARI ανάμεσα στην ομαδοποίηση των καταγεγραμμένων paths και των ίδιων paths με θόρυβο στο ελεύθερο μήκος. Από τους Ben-Hur, Elisseeff, Guyon (PSB 2002) και von Luxburg (FnT ML 2010) παίρνουμε την ιδέα ότι **η σταθερότητα υπό διαταραχή είναι κριτήριο εγκυρότητας όταν δεν υπάρχει GT**. ARI: Hubert & Arabie, J. Classification 1985.
3. **Ετικέτες στόχου σύγκρουσης**: mixed και over-split (§ παραπάνω), για fixed-near, fixed-far, dynamic-no-split, dynamic-split. **Αυτή είναι η πιο άμεση τεκμηρίωση του split.**
4. Ρυθμός split ως συνάρτηση της απόστασης από το πλησιέστερο εμπόδιο: ❌ δεν υλοποιήθηκε ακόμα.

- ID switches και fragmentations ανά λεπτό, με αναφορά τη συνέχεια γωνιακών διαστημάτων (IoU). Από το CLEAR MOT (Bernardin & Stiefelhagen 2008) και το IDF1 (Ristani et al. 2016) παίρνουμε μόνο τους **ορισμούς** των μετρικών.
- Σύγκριση: dynamic με αντιστοίχιση `upstream` έναντι `tracking`, offline πάνω στα ίδια clusters και online με τη ρύθμιση στο yaml. Ο fixed μένει baseline.
- Downstream επίδραση: πόσες φορές αλλάζει το MAP cluster του estimator χωρίς να αλλάξει η εντολή του χρήστη. ❌ Δεν υλοποιήθηκε ακόμα. Τα δεδομένα υπάρχουν στο `intent_diagnostics`.



**Ορισμοί** (έλεγχοι φυσικής συνέπειας, χωρίς ground truth). Τα διαστήματα είναι στα 1.8 m, και το προηγούμενο frame στρέφεται κατά τη στροφή του ρομπότ.
- **ID switch**: δύο διαδοχικά clusters με $J \ge 0.5$ (σχεδόν ίδιο γωνιακό διάστημα, άρα ίδιο πέρασμα) αλλά διαφορετικό ID.
- **Fragmentation**: ένα πέρασμα χάνεται και ξαναβρίσκεται μέσα σε 0.5 s με άλλο ID.
- **ID crossing**: δύο IDs αλλάζουν σειρά κατά φ μεταξύ διαδοχικών frames (αδύνατο φυσικά).
- **Duplicate IDs**: frames με το ίδιο ID δύο φορές (πρέπει να είναι 0· ο upstream δεν το εγγυάται, Β2).
- **Αστήρικτη κληρονομιά**: ίδιο ID σε διαδοχικά frames ενώ $J < 0.1$.


## Επίπεδο 3: επιλογή (SCAND)
- **Ground truth πρόθεσης**: η καταγεγραμμένη μελλοντική διαδρομή του οδηγού (SCAND, Karnan et al., RA-L 2022: οι επιδείξεις ανθρώπων ως αναφορά συμπεριφοράς).
- **α) Cluster hit**: φ_true = γωνία στην οποία η πραγματική διαδρομή βγαίνει από τον κύκλο 1.8 m. Hit αν φ_true ∈ [φ_min, φ_max] του MAP cluster.
  - Επειδή ο estimator δίνει **κατανομή**, μετράμε και **Brier score** (Brier 1950) και **log-loss** της πιθανότητας του σωστού cluster (proper scoring rules).
- **β) Απόσταση path**: |φ* − φ_true| στον ορίζοντα και ADE/FDE σε ίσο μήκος τόξου (ορισμοί από την πρόβλεψη τροχιών, π.χ. Alahi et al., *Social LSTM*, CVPR 2016). Το discrete Fréchet (Eiter & Mannila 1994) δεν υλοποιήθηκε.
- **Baselines**: cluster που περιέχει το φ_user, ομοιόμορφη κατανομή, τόξο με την καμπυλότητα ω/v της εντολής («μόνο χρήστης»).
- ✅ Τι εννοούσα με «baseline μόνο χρήστης» και «εξαιρέσεις»: βλ. § SCAND πειράματα.
